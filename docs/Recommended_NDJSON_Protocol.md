Recommended NDJSON Protocol

1. Protocol framing

The backend returns an HTTP streaming response with the media type:

application/x-ndjson

Each application event is serialized as one JSON object followed by a newline character.

The frontend must interpret the response as a sequence of newline-delimited records, not as:

One complete JSON document
A JSON array
Server-Sent Events
One JSON object per network read
One LangChain chunk per network read

A network byte chunk can contain:

Part of one NDJSON record
Exactly one record
Multiple records
The end of one record and the beginning of another

The newline inserted by to_ndjson() is the authoritative record boundary.

2. Event sequence

For a successful request, the expected logical sequence is:

One start event
Zero or more token, tool_call_delta, and tool_result events
One done event

A simple response without tools would follow this sequence:

start
token
token
token
done

A response involving one tool might follow this sequence:

start
token
tool_call_delta
tool_call_delta
tool_call_delta
tool_result
token
token
done

A failed stream would normally follow this sequence:

start
zero or more intermediate events
error

The backend implementation does not emit done after an exception. Therefore, error is a terminal event.

If the client disconnects and causes GeneratorExit, the backend logs the disconnection and does not emit either error or done.

3. start event
   Purpose

The start event indicates that the backend has entered the stream generator and started processing the chat request.

It is emitted before LangChain stream events are processed.

Exact fields

The event contains:

type
Always "start".
thread_id
The thread ID received in the original request.
Representative wire record
{"type":"start","thread_id":"thread-123"}

The physical response also contains a newline immediately after the closing brace.

Frontend behavior

Upon receiving this event, the frontend should:

Mark the request as accepted.
Mark the assistant placeholder as streaming.
Associate the active request with the returned thread ID.
Start or update timing metrics.
Confirm that the event belongs to the expected conversation.

The frontend should not interpret start as evidence that the model has generated content. It only confirms that backend stream processing has begun.

4. token event
   Purpose

The token event contains incremental assistant-generated text extracted from an AIMessageChunk.

The backend emits this event only when its text extraction function returns a non-empty string.

Exact fields

The event contains:

type
Always "token".
content
The incremental text fragment.
node
The value of metadata["langgraph_node"], if present.
It may be a string or null.
Representative wire record
{"type":"token","content":"Here is what I found","node":"model"}

Content semantics

The content field is a delta, not the complete assistant answer.

The frontend must append it to the existing assistant message:

assistant content = previous assistant content + event content

The frontend must not:

Replace the entire assistant message with each token.
Trim each token.
Add spaces between tokens automatically.
Create one chat bubble per token.
Assume each token is a complete word.
Assume each token is valid standalone Markdown.

Spaces, newlines, and punctuation inside content must be preserved exactly.

Node handling

The node value is metadata identifying the graph node that produced the event.

The frontend may use it for:

Diagnostics
Development tools
Filtering
Agent activity labels
Telemetry

The frontend should not require node to render assistant text. A null node must be accepted.

5. tool_call_delta event
   Purpose

The tool_call_delta event carries a fragment of a tool call generated by the model.

A complete tool call may be spread across multiple events. The tool name, ID, and arguments are not guaranteed to arrive together.

Exact fields

The event contains:

type
Always "tool_call_delta".
tool_name
The name of the tool when supplied by the current LangChain chunk.
May be null.
tool_call_id
The tool-call identifier when supplied by the current chunk.
May be null.
tool_call_index
The position of the tool call in the model output.
May be an integer or null.
args_delta
The tool argument fragment from the current chunk.
Always normalized to a string by the improved backend.
May be an empty string.
node
The LangGraph node from the event metadata.
May be a string or null.
Representative first tool-call record
{"type":"tool_call_delta","tool_name":"search","tool_call_id":"call-1","tool_call_index":0,"args_delta":"","node":"model"}

Representative later argument record
{"type":"tool_call_delta","tool_name":null,"tool_call_id":null,"tool_call_index":0,"args_delta":"{\"query\":\"streaming","node":"model"}

Representative final argument fragment
{"type":"tool_call_delta","tool_name":null,"tool_call_id":null,"tool_call_index":0,"args_delta":" chatbot\"}","node":"model"}

Frontend accumulation requirements

The frontend must maintain one tool-call record per logical tool operation.

For each new delta, it must:

Identify the corresponding tool call.
Retain any previously received tool name.
Retain any previously received tool-call ID.
Append args_delta to the existing argument string.
Update the tool-call status and presentation.

A null field means that the current delta does not repeat that value. It does not mean that a previously known value should be erased.

For example, if the first event supplies:

tool_name = search

and the next event supplies:

tool_name = null

the frontend must continue treating the tool name as search.

Correlation priority

The frontend should correlate tool-call deltas in this order:

tool_call_id, when present
tool_call_index, scoped to the active assistant response
A temporary first-seen identifier if both are unavailable

Once a real tool_call_id arrives, the frontend should attach it to the existing temporary tool-call record rather than create another record.

Argument parsing

The accumulated argument value may eventually become valid JSON, but each args_delta is only a string fragment.

The frontend must not treat an individual fragment as a complete argument object.

Argument JSON parsing should occur only when:

The accumulated string appears complete, or
A subsequent protocol event indicates that the tool call has progressed to execution.

A parse failure during accumulation is normally an incomplete-data condition, not a user-visible error.

6. tool_result event
   Purpose

The tool_result event represents a completed tool execution result provided as a ToolMessage.

Exact fields

The event contains:

type
Always "tool_result".
tool_name
The name associated with the ToolMessage.
May be a string or null, depending on the message.
tool_call_id
The identifier linking the result to the originating tool call.
content
The tool result.
It may be a string or another JSON-serializable structure.
status
The tool status when available on the ToolMessage.
It may be a string or null.
node
The LangGraph node from event metadata.
It may be a string or null.
Representative wire record
{"type":"tool_result","tool_name":"search","tool_call_id":"call-1","content":"Search completed successfully.","status":"success","node":"tools"}

Frontend correlation behavior

The frontend must use tool_call_id as the primary correlation key.

When the matching record is found, it should:

Attach the result to that tool call.
Mark the tool call as completed or failed.
Store the completion time.
Stop displaying an active progress indicator.
Update any expandable tool details.

If no matching tool_call_id exists, the frontend should not discard the result. It should create an unmatched tool-result record and record a protocol warning for diagnostics.

Content handling

The frontend must not assume content is always plain text.

Because the backend passes token.content through jsonable_encoder, the resulting value may be:

A string
A list
A dictionary-like object
Another JSON-compatible structure

The tool-result renderer must inspect the runtime value before displaying it.

Structured tool content should use an appropriate structured renderer or a sanitized serialized representation. It must never be inserted as raw HTML.

Status handling

A null status means that the ToolMessage did not expose a status value. It does not necessarily mean the tool failed.

The frontend may infer basic completion from receiving tool_result, but should use the explicit status when available.

7. done event
   Purpose

The done event indicates that the backend completed iteration over chatbot.stream() without an exception.

Exact fields

The event contains only:

type
Always "done".
Representative wire record
{"type":"done"}

Frontend behavior

Upon receiving done, the frontend should:

Mark the assistant message as completed.
Stop all streaming indicators.
Finalize Markdown and syntax highlighting.
Finalize tool-call presentation.
Record completion metrics.
Re-enable message submission where appropriate.
Release temporary stream-specific state after the physical response closes.

The frontend should not expect additional content events after done.

If additional events arrive, they should be ignored or logged as a protocol violation.

Application completion versus transport completion

done represents successful application completion.

The later reader.read() result with done: true represents physical HTTP response closure.

These are not identical.

The ideal successful lifecycle is:

NDJSON done event
HTTP stream closes
reader reports done

If the HTTP stream closes without an NDJSON done or error event, the response should be classified as interrupted.

8. error event
   Purpose

The error event indicates that an exception occurred during backend stream processing after the streaming response had begun.

Exact fields

The improved backend emits:

type
Always "error".
message
A user-safe error description.
Exact message from the proposed backend

The current improved backend returns:

The chatbot response stream failed.

Representative wire record
{"type":"error","message":"The chatbot response stream failed."}

Frontend behavior

Upon receiving error, the frontend should:

Mark the request as failed.
Preserve any assistant content already received.
Mark the response as incomplete.
Stop token and tool progress indicators.
Display the safe error message.
Offer retry where appropriate.
Prevent subsequent events from modifying the failed message.

The frontend must not expect a done event after error.

The backend catches the exception, emits error, and then the generator ends. Therefore, physical stream closure should follow.

HTTP status implication

Because the error may occur after response headers were already sent, the HTTP status may still be successful.

The frontend must therefore evaluate both:

The initial HTTP status
Application-level NDJSON events

A successful HTTP status does not guarantee a successful chatbot response.

9. Full representative successful stream

A complete tool-assisted response could arrive logically as follows:

{"type":"start","thread_id":"thread-123"}
{"type":"token","content":"I will check that for you.","node":"model"}
{"type":"tool_call_delta","tool_name":"search","tool_call_id":"call-1","tool_call_index":0,"args_delta":"","node":"model"}
{"type":"tool_call_delta","tool_name":null,"tool_call_id":null,"tool_call_index":0,"args_delta":"{\"query\":\"LangChain","node":"model"}
{"type":"tool_call_delta","tool_name":null,"tool_call_id":null,"tool_call_index":0,"args_delta":" streaming\"}","node":"model"}
{"type":"tool_result","tool_name":"search","tool_call_id":"call-1","content":"Search completed successfully.","status":"success","node":"tools"}
{"type":"token","content":"The search has completed.","node":"model"}
{"type":"done"}

Each object is a separate NDJSON record and is followed by a newline on the wire.

This is a representative sequence, but the number and ordering of intermediate events can vary.

10. Full representative failed stream

If the backend fails after generating partial content, the stream could be:

{"type":"start","thread_id":"thread-123"}
{"type":"token","content":"I found part of the answer","node":"model"}
{"type":"error","message":"The chatbot response stream failed."}

There is no done event in this case.

The frontend should retain:

I found part of the answer

but mark it as incomplete.

11. Exact frontend event model

The frontend protocol model should recognize these event shapes:

Start event
type: "start"
thread_id: string

Token event
type: "token"
content: string
node: string or null

Tool-call delta event
type: "tool_call_delta"
tool_name: string or null
tool_call_id: string or null
tool_call_index: integer or null
args_delta: string
node: string or null

Tool-result event
type: "tool_result"
tool_name: string or null
tool_call_id: string or null
content: any JSON-compatible value
status: string or null
node: string or null

Done event
type: "done"

Error event
type: "error"
message: string

The frontend should validate these fields at runtime even if it uses a statically typed language.

12. Important limitation of the exact protocol

The current improved backend sends argument fragments through tool_call_delta, but it does not send a separate event indicating that tool-call argument generation is complete.

The frontend can usually infer progression when it receives the matching tool_result, but it cannot always know the exact moment when:

generating tool arguments

became:

executing the tool

For the exact current backend contract, the frontend should use these practical states:

First tool_call_delta

Status: preparing tool call

Additional tool_call_delta events

Status: generating tool arguments

Matching tool_result

Status: completed or failed

If the product requires a distinct visible “tool is running” state, the backend protocol would need an additional event, such as tool_started. That event is not returned by the current improved implementation and therefore should not be assumed by the frontend.

13. Terminal-state rules

The frontend should use the following terminal-state rules.

Successful terminal state

The request is successful only when:

A valid done event was received.
Failed terminal state

The request failed when:

A valid error event was received.
A fatal parsing or protocol error occurred.
The initial HTTP request failed.
Cancelled terminal state

The request was cancelled when:

The frontend intentionally aborted it.
Interrupted terminal state

The request was interrupted when:

The HTTP response closed without done or error.
The network connection ended unexpectedly.
The browser lost access to the response body.

This distinction prevents a partial response from being incorrectly presented as complete.

Clarification and improvement

The missing part of the earlier specification was the precise mapping between backend output and frontend behavior. The protocol above now mirrors the improved backend exactly: start, token, tool_call_delta, tool_result, done, and error, including nullable metadata, incremental tool arguments, terminal-event semantics, and the fact that the current backend does not emit a dedicated tool-execution-start event.
