Below is a frontend technical requirements specification for integrating with the improved synchronous .stream() backend. It focuses on transport handling, NDJSON parsing, event processing, UI state management, tool-call presentation, resilience, security, accessibility, and testing, without prescribing a particular frontend framework.

Frontend Technical Requirements for the Streaming Chatbot

1. Integration objective

The frontend must provide a responsive conversational interface that consumes the backend’s streaming HTTP response incrementally.

It must support the following sequence:

Submit the user message through an HTTP POST request.
receive the response as a readable byte stream.
Decode incoming byte chunks as UTF-8 text.
Preserve incomplete NDJSON records between reads.
Parse each complete NDJSON object.
Dispatch each object according to its explicit event type.
Incrementally update the assistant response.
Display tool-call progress and tool results.
Handle completion, cancellation, malformed events, network failures, and backend-reported errors.

The frontend must not wait for the entire response before displaying assistant content.

2. Supported backend contract
   2.1 Request contract

The frontend must submit a JSON request containing:

user_input
The user’s current message.
Must be a non-empty string after validation.
thread_id
A stable identifier for the conversation.
Must remain consistent across messages in the same conversation.
Must change when the user starts a new conversation.

The request must use:

HTTP method: POST
Request content type: application/json
Expected response type: application/x-ndjson

The frontend should also include any authentication, tenant, workspace, locale, or tracing headers required by the wider application.

2.2 Response contract

The frontend must treat the response as a sequence of independent JSON objects separated by newline characters.

Each JSON object represents one application-level stream event. The frontend must not assume that:

One network chunk contains one event.
A network chunk ends at a newline.
One event arrives in a single network chunk.
A network chunk contains valid JSON by itself.
All event types contain the same fields.
Tool arguments arrive as complete JSON.
Tool name and tool-call ID are repeated in every tool delta.
2.3 Required event types

The frontend should support at least the following event types:

start

Indicates that the backend accepted the request and started processing it.

Expected information may include:

Conversation or thread ID
Run identifier
Request identifier
Server timestamp

The frontend should use this event to move the pending assistant response into a streaming state.

token

Contains an incremental portion of assistant-generated text.

Expected information:

Text content
Optional graph-node metadata
Optional message or run identifier

The frontend must append the content to the current assistant message rather than create a separate message for every token.

tool_call_delta

Contains a partial update for a tool call being generated by the model.

Expected information may include:

Tool name
Tool-call ID
Tool-call index
Tool argument fragment
Graph-node metadata

The tool name or ID may be absent from later fragments. The frontend must retain previously received values.

tool_result

Contains the completed result of a tool execution.

Expected information may include:

Tool name
Tool-call ID
Result content
Tool execution status
Graph-node metadata

The frontend must correlate the result with the appropriate tool call.

done

Indicates successful completion of the application-level stream.

The frontend should use this event to finalize the assistant message and clear the streaming state.

error

Indicates that the backend encountered an error after the HTTP response had already started.

Expected information may include:

User-safe error message
Error category
Retryability indicator
Request or run identifier

The frontend must stop showing a normal loading state and present an appropriate failure state.

Optional heartbeat

Indicates that the connection is still active during a long-running operation.

A heartbeat must not alter conversation content. It may update an internal last-activity timestamp.

3. Streaming transport requirements
   3.1 Browser capability

The target browser environment must support:

HTTP streaming through the Fetch API
Readable response bodies
Stream readers
UTF-8 text decoding
Request cancellation through an abort signal
Standard JSON parsing

If older or embedded browsers must be supported, the frontend must define:

A compatibility policy
A browser support matrix
A fallback experience for unsupported streaming
Appropriate polyfills where technically possible

When streaming is unavailable, the UI should either fall back to a non-streaming endpoint or present a clear compatibility message.

3.2 Response validation

Before reading the stream, the frontend must verify:

The HTTP request completed successfully.
The HTTP status is acceptable.
A readable response body exists.
The response content type is compatible with NDJSON.
Authentication has not expired.
The response was not redirected to an authentication or error page.

If the server returns a non-success status before streaming begins, the frontend should process it as a normal HTTP error rather than as NDJSON.

3.3 Byte decoding

Incoming data will arrive as bytes and must be decoded as UTF-8.

The decoder must operate in streaming mode so that a multibyte character split across two network reads is not corrupted.

At the end of the response, the decoder must be flushed to retrieve any internally buffered character data.

3.4 NDJSON buffering

The frontend must maintain a persistent text buffer for the duration of the response.

For each decoded text fragment, it must:

Append the fragment to the existing buffer.
Identify complete newline-terminated records.
Remove and process complete records.
Preserve the final incomplete record in the buffer.
Continue the process after the next network read.

When the transport closes, the frontend must inspect the remaining buffer. A final non-empty record should be parsed even if the backend closed the stream without a trailing newline.

Blank lines should be safely ignored.

The frontend should also tolerate carriage-return and newline line endings by removing a trailing carriage return before JSON parsing.

3.5 Completion distinction

The frontend must distinguish between:

Receiving a done event
Reaching the physical end of the HTTP response

A done event means the application completed successfully. Physical connection closure only means that no additional bytes are available.

If the connection closes without a done or error event, the frontend should classify the outcome as an interrupted or incomplete response unless the backend contract explicitly states otherwise.

4. Event validation and dispatch
   4.1 Event discriminator

Every event must be dispatched based on its explicit type field.

The frontend must not infer the event type solely from the presence of fields such as:

content
tool_name
tool_call_id

This protects the client from ambiguity between assistant content, tool arguments, and tool results.

4.2 Runtime validation

Static language types alone are insufficient because incoming JSON is untrusted runtime data.

The frontend should perform runtime validation for every event, including:

The event is a JSON object.
The type property exists and is a string.
Required fields for the event type are present.
Field values have acceptable data types.
String and payload sizes are within reasonable limits.
Unknown fields do not break processing.

Invalid events should be handled according to severity:

A harmless unknown field should be ignored.
An unsupported event type should be logged and skipped.
A malformed content event may be skipped if processing can safely continue.
A malformed protocol-critical event should terminate the stream with a protocol error.
4.3 Protocol versioning

The wire protocol should include a versioning strategy.

This may be represented by:

A response header
A version field in the start event
A version field on every event

The frontend must define how it behaves when it receives:

The currently supported version
An older compatible version
A newer unsupported version

Protocol versioning prevents future backend changes from silently breaking the UI.

4.4 Forward compatibility

Unknown event types should not automatically crash the entire conversation.

The frontend should:

Record diagnostic information.
Ignore the event when safe.
Continue reading subsequent events.
Surface a generic error only when the unknown event prevents correct rendering. 5. Conversation data model
5.1 Conversation entity

Each conversation should contain:

Thread ID
Conversation title
Creation time
Last update time
Message collection
Current conversation status
Optional server-side conversation reference
Optional model or agent configuration

The thread ID must be treated as part of the backend memory contract. Reusing a thread ID for an unrelated conversation could mix conversation history.

5.2 Message entity

Each message should have a stable client-side identifier and should contain:

Message ID
Role
Text content
Creation time
Status
Associated thread ID
Optional request or run ID
Tool activities associated with the message
Error metadata
Retry metadata
Completion reason, if available

Recommended message roles include:

User
Assistant
System
Tool

Tool activity may be stored separately from visible chat messages if the product design presents tools as expandable status items within the assistant message.

5.3 Message status model

Assistant messages should support at least these states:

pending
streaming
waiting_for_tool
completed
cancelled
interrupted
error

The UI must ensure valid transitions. For example:

A message begins as pending.
The start event moves it to streaming.
Tool activity may move it to waiting for tool.
Additional tokens return it to streaming.
The done event moves it to completed.
Cancellation moves it to cancelled.
An unexpected disconnection moves it to interrupted.
A backend error moves it to error.
5.4 Single active assistant message

For each submitted user message, the frontend should create one assistant response placeholder.

All token events belonging to that request must update the same assistant message. This prevents:

One message bubble per token
Incorrect ordering
Excessive component creation
Difficult persistence and retry behavior 6. Incremental assistant response rendering
6.1 Token accumulation

Each token event must append its text to an in-memory response accumulator.

The UI should render the accumulated content progressively.

The frontend must preserve:

Whitespace
Paragraph boundaries
Punctuation
Unicode characters
Markdown delimiters that span token events

It must not trim every token because leading spaces are often semantically important in streamed language output.

6.2 Render batching

Directly rerendering the full chat interface for every token may cause poor performance.

The frontend should batch visual updates using an appropriate scheduling strategy, such as:

Animation-frame batching
Short timed batches
Buffered state updates
Local mutable accumulation followed by periodic committed rendering

The batching interval must balance:

Perceived responsiveness
CPU usage
Battery consumption
Layout recalculation
Screen-reader behavior

The raw stream accumulator should remain complete even if visual updates are batched.

6.3 Markdown rendering

If assistant content supports Markdown, the frontend renderer must handle incomplete syntax during streaming.

Examples include:

Unclosed emphasis
Incomplete links
Partial headings
Unclosed lists
Unclosed code fences
Partially received tables

The renderer should not throw errors when the current content is syntactically incomplete.

A practical design is to provide:

Lightweight, tolerant rendering while streaming
A final full render after the done event
6.4 Code blocks

If the chatbot can generate code, the frontend should avoid expensive syntax highlighting on every token.

Syntax highlighting should be:

Delayed until a code block is sufficiently complete
Throttled during streaming
Fully applied after completion

Copy controls should operate on the final underlying text rather than on styled HTML.

6.5 Rich content

If future events support citations, files, images, or structured cards, these should use dedicated structured event fields rather than embedding unsafe markup in assistant text.

The initial frontend architecture should allow new renderable content blocks to be added without rewriting the transport layer.

7. Tool-call lifecycle requirements
   7.1 Tool-call correlation

The frontend must track each tool operation independently.

The primary correlation key should be the tool_call_id.

Because early tool deltas may not contain an ID, the frontend should temporarily correlate them using:

Tool-call index
Request or run ID
Graph-node identifier
Stream order scoped to the current assistant response

When a later event supplies the real tool-call ID, the frontend should merge the temporary record into the identified record.

7.2 Tool-call accumulation

For every tool call, the frontend should maintain:

Tool-call ID
Temporary correlation key
Tool-call index
Tool name
Accumulated argument text
Parsed arguments, when valid
Status
Start time
Completion time
Tool result
Error information

Tool argument deltas must be concatenated in arrival order.

The frontend must not attempt to parse the accumulated arguments after every fragment as though each fragment were complete JSON. Parsing may be attempted opportunistically, but parse failure must be treated as an expected incomplete state until the tool call is known to be complete.

7.3 Tool display states

A tool activity component should support states such as:

Preparing tool request
Generating arguments
Running
Completed
Failed
Cancelled

The UI should avoid displaying misleading information. For example, it should not label a tool as running while the model is still generating its arguments unless that distinction is intentionally hidden from users.

7.4 Tool-name handling

The tool name may be unavailable in the first renderable moment.

The frontend should initially display a neutral status such as:

Preparing an action
Selecting a tool
Processing request

It can replace that label when the tool name arrives.

Internal tool identifiers should be mapped to user-friendly labels. For example, an internal function name should not automatically become the visible user label.

7.5 Tool-result rendering

Tool results must be associated with their originating call.

The frontend must determine whether the result should be:

Hidden and used only to inform the final answer
Shown as a short status summary
Available in an expandable details section
Rendered as structured information
Presented as an error

Raw tool output must not automatically be inserted as trusted HTML.

7.6 Parallel tool calls

The frontend architecture must support more than one active tool call.

It must not rely on a single global tool status. Each tool call requires separate:

Identity
Arguments
Progress state
Result
Error state

Parallel calls should be displayed in a stable order, preferably based on their tool-call index or first-seen order.

8. User interaction requirements
   8.1 Message submission

The composer must:

Prevent submission of empty messages.
Disable duplicate submission while dispatching the same request.
Preserve the submitted user message in the conversation immediately.
Create an assistant placeholder immediately.
Clearly indicate that processing has begun.
Retain the original message for retry purposes.
Support keyboard and pointer submission.
Avoid accidental multiple requests from rapid repeated input.

Whether users may submit another message while one is streaming must be an explicit product decision.

Recommended initial rule

Allow one active generation per conversation. Disable or queue additional messages until the current stream ends.

This avoids race conditions involving shared thread memory and message ordering.

8.2 Stop generation

The interface should provide a stop control while a request is active.

Stopping must:

Abort the browser request.
Stop reading the response stream.
Preserve content already received.
Mark the assistant response as cancelled.
Stop loading indicators.
Prevent subsequent events from modifying the cancelled message.
Release stream-reader resources.

Cancellation must be distinguished from an application failure. It should not display a generic error message when the user intentionally stopped the response.

8.3 Retry behavior

The UI should offer retry for:

Pre-stream HTTP failures
Network interruptions
Backend-reported retryable errors
Incomplete responses

Retry semantics must be defined carefully. The frontend should know whether retry means:

Resend the original user message in the same thread
Regenerate from the current conversation state
Create a new request in a new branch
Replace the incomplete assistant response

Blindly resending the same message may duplicate conversation state if the backend stored the first attempt before the connection failed.

For reliable retries, the broader protocol should support an idempotency or request identifier.

8.4 New conversation

Starting a new conversation must:

Generate or obtain a new thread ID.
Cancel any active stream in the current thread if necessary.
Clear conversation-specific UI state.
Clear temporary tool-call indexes and buffers.
Prevent late events from the old request from appearing in the new conversation.
8.5 Conversation switching

If the UI supports multiple conversations, every active request must remain scoped to its conversation and assistant message.

Events from a background conversation must never update whichever conversation is currently visible by accident.

9. Concurrency and stale-event protection

Each chat request should have a client-generated request ID, even if the initial backend does not require one.

At event-dispatch time, the frontend should confirm that:

The request is still active.
The event belongs to the expected conversation.
The target assistant message still exists.
The request has not been cancelled.
A newer request has not superseded the current one.

This prevents stale asynchronous operations from updating the wrong message after:

Navigation
Conversation switching
Retry
Cancellation
Component unmounting
Network delay

All parsing buffers, tool records, and rendering accumulators should be scoped to an individual request rather than stored as global mutable data.

10. Error-handling requirements
    10.1 Error categories

The frontend should distinguish between:

Request validation failure
Authentication or authorization failure
Rate limit
Server rejection before streaming
Network disconnection
Stream protocol error
Malformed NDJSON
Unsupported protocol version
Backend error event
Client cancellation
Rendering failure
Tool execution failure
Stream closure without done

Different error classes should produce different user actions and telemetry.

10.2 Partial response preservation

If failure occurs after content has been received, the frontend should preserve the partial response.

The message should be clearly marked as incomplete and may provide actions such as:

Retry
Continue
Copy partial response
Submit a follow-up message

The UI should not silently present an interrupted response as complete.

10.3 JSON parse failures

A JSON parse error must not automatically be treated as an incomplete record if that record was already newline-terminated.

A newline-terminated but invalid JSON record indicates a protocol or server serialization problem.

The frontend should:

Record the raw line in restricted diagnostic telemetry where permitted.
Avoid exposing sensitive raw data to end users.
Decide whether processing subsequent records is safe.
Terminate the stream if state consistency cannot be guaranteed.
10.4 Timeout and inactivity handling

The frontend should distinguish between:

Total request timeout
Connection timeout
Inactivity timeout
Long but valid tool execution

An inactivity timer may be refreshed whenever the client receives:

A token
A tool delta
A tool result
A heartbeat
Any other valid stream event

Timeout values should reflect realistic agent and tool execution times. A tool request may remain valid even when no assistant text is being produced.

11. Security requirements
    11.1 Untrusted content handling

All assistant content, tool arguments, and tool results must be treated as untrusted data.

The frontend must not:

Insert raw stream content directly into the document as HTML.
Execute script content.
Evaluate tool arguments.
Treat model-generated URLs as automatically trusted.
Render arbitrary tool output inside privileged components.
Execute model-generated code.

If Markdown supports embedded HTML, raw HTML should be disabled or sanitized through an approved sanitization policy.

11.2 Link handling

Links generated by the assistant should:

Use validated URL schemes.
Reject dangerous schemes.
Clearly indicate external navigation where appropriate.
Use safe new-window behavior when opening another tab.
Avoid forwarding sensitive application state through query parameters.
11.3 Sensitive data

The frontend should avoid logging:

User prompts
Assistant responses
Full tool arguments
Tool results
Authentication tokens
Personal or confidential information

When diagnostic logging is necessary, it should use:

Redaction
Sampling
Access control
Retention limits
Environment-specific configuration
11.4 Authentication

If the API uses cookies, the request must conform to the application’s cross-site request forgery protections.

If it uses bearer tokens, token handling must follow the application’s secure credential-storage policy.

Authentication expiration during a stream should result in a clear recoverable state rather than an endless loading indicator.

11.5 Resource limits

The frontend should enforce reasonable limits for:

User message length
Accumulated assistant response length
Maximum NDJSON line length
Tool argument size
Tool result size
Number of concurrent tool calls
Number of conversations retained in memory

These limits protect the interface against accidental or malicious memory exhaustion.

12. Accessibility requirements

The streaming experience must remain usable with assistive technology.

12.1 Screen-reader announcements

The UI should not announce every token because this can overwhelm screen-reader users.

Instead, it should:

Announce that the assistant has started responding.
Update the visible content without excessively triggering live-region announcements.
Announce significant tool status changes.
Announce completion or failure.
Offer access to the final complete response.

A restrained live-region strategy is preferable to making the entire changing assistant message highly assertive.

12.2 Keyboard support

Users must be able to:

Focus the message composer.
Submit a message.
Stop generation.
Retry an unsuccessful request.
Expand or collapse tool details.
Copy content.
Navigate conversation controls.

Focus must not automatically jump with every streaming update.

12.3 Visual status communication

Streaming and tool states must not rely on color alone.

Use combinations of:

Text labels
Icons
Progress indicators
Accessible status descriptions
Consistent placement

Animations should respect reduced-motion preferences.

12.4 Auto-scrolling accessibility

Automatic scrolling must not continually pull the user away from content they are reviewing.

If the user scrolls away from the bottom:

Auto-follow should pause.
A “new content” or “jump to latest” control should appear.
Streaming should continue without changing the user’s reading position. 13. Chat layout and visual behavior
13.1 Required interface areas

The initial UI should include:

Conversation history area
Distinct user and assistant messages
Message composer
Send control
Stop-generation control
Streaming indicator
Tool activity area
Error and retry controls
New-conversation control
Connection or recovery feedback where necessary
13.2 Assistant response states

The assistant message should visibly distinguish:

Waiting for first content
Receiving content
Running a tool
Completed
Cancelled
Interrupted
Failed

The interface should avoid showing a generic typing indicator after actual text has started appearing unless it communicates continued processing.

13.3 Tool presentation

Tool details should generally be collapsible to avoid overwhelming the conversation.

The collapsed presentation might communicate:

Action being performed
Current status
Success or failure
Duration

Expanded details may show sanitized arguments and results if the product’s audience requires technical transparency.

13.4 Auto-scroll behavior

The chat should follow new content only when the user is already near the bottom.

The frontend must avoid scrolling on every token if this causes visual jitter. Scroll updates should be throttled or tied to render batches.

14. Performance requirements
    14.1 Rendering efficiency

The frontend must avoid reconstructing the entire conversation for every token.

Recommended architectural characteristics include:

Stable message identifiers
Component-level isolation
Memoized historical message rendering
Local accumulation for the active message
Batched state commits
Virtualization for long conversations, where needed
14.2 Memory management

When a stream terminates, the frontend must:

Release the reader lock.
Clear timers.
Clear temporary buffers.
Remove abort listeners.
Finalize or discard temporary tool correlations.
Prevent further callbacks from updating disposed components.

Conversation history should be persisted or unloaded according to the application’s data-retention strategy rather than retained indefinitely in browser memory.

14.3 Large responses

The UI should remain functional for long assistant responses and large tool outputs.

Potential controls include:

Collapsing verbose tool results
Limiting initial rendering
Progressive expansion
Virtualized message history
Deferred syntax highlighting
Size-based warnings 15. Persistence requirements

If conversation history must survive a page reload, the frontend needs a defined persistence source.

15.1 Server-authoritative history

This is generally preferable where the backend already maintains thread-based state.

The frontend should reload messages from a dedicated conversation-history endpoint rather than assume that the local browser state is authoritative.

15.2 Local draft state

The browser may locally preserve:

Unsubmitted composer drafts
Current conversation selection
UI preferences
Expanded tool panels
Scroll position

Sensitive conversation content should not be placed in persistent browser storage unless approved by the application’s security and privacy requirements.

15.3 In-flight reload behavior

A page reload normally terminates the active fetch connection.

The product must define whether the user sees:

The partial response as interrupted
A reconstructed completed response from server history
An option to reconnect
An option to retry

Reliable reconnection requires additional backend support, such as resumable event IDs or run-status retrieval. It cannot be guaranteed by the basic NDJSON stream alone.

16. Observability requirements

The frontend should capture operational metrics without recording confidential content.

Useful measurements include:

Time to request acceptance
Time to first stream event
Time to first visible token
Total response duration
Number of received events
Number and duration of tool calls
Completion rate
Cancellation rate
Stream interruption rate
NDJSON parse-error rate
Backend error-event rate
Retry rate
Average render frequency

Correlation identifiers should connect frontend telemetry to backend traces without exposing private message data.

The start event is a useful place for the backend to provide a safe run or trace identifier.

A cancelled message

Seeing tool status

17.5 Cross-browser testing

Testing should cover all officially supported:

Desktop browsers

18. Recommended frontend architecture

The frontend should separate the implementation into five logical layers.

Transport layer

Responsible for:

Sending the request
Reading bytes
Cancellation
Detecting HTTP errors
Detecting connection closure
NDJSON parser layer

Responsible for:

UTF-8 streaming decode
Text buffering
Newline framing
JSON parsing
Protocol-size limits
Protocol layer

Responsible for:

Runtime event validation
Event-type dispatch
Protocol version handling
Unknown-event behavior
Conversation state layer

Responsible for:

Conversations and thread IDs
Messages and statuses
Token accumulation
Tool-call correlation
Completion and failure transitions
Stale-request protection
Presentation layer

Responsible for:

Chat layout
Assistant progressive rendering
Tool status display
Scrolling
Accessibility
Retry and cancellation controls

This separation is important because NDJSON framing should not be mixed directly into UI components. It also makes the stream parser and protocol handling independently testable.

19. Acceptance criteria

The frontend integration should be considered complete when it satisfies all of the following:

Assistant text begins appearing before the backend finishes.
Unicode content remains correct when characters are divided across byte chunks.
NDJSON objects are parsed correctly regardless of transport chunk boundaries.
A partial NDJSON line is retained until completed.
Token events update one assistant message rather than creating multiple messages.
Multiple tool calls are tracked independently.
Tool argument fragments are accumulated in order.
Tool results are matched through their tool-call IDs.
Unknown safe events do not crash the conversation.
A done event finalizes the response.
Connection closure without done is recognized as incomplete.
A backend error event creates a controlled error state.
User cancellation stops the request and preserves received content.
Late events cannot update a cancelled or unrelated conversation.
Markdown and code rendering tolerate incomplete streamed syntax.
Raw model or tool content cannot execute as active HTML or script.
Auto-scroll pauses when the user reads earlier content.
The interface is keyboard accessible and does not announce every token.
Diagnostic metrics can correlate frontend requests with backend runs.
The complete behavior works through the production proxy, gateway, and authentication path.
Design rationale

These requirements separate transport framing, protocol interpretation, application state, and visual rendering. That separation is essential for safely consuming synchronous .stream() output because HTTP byte boundaries, NDJSON message boundaries, LangChain token boundaries, tool-call boundaries, and UI rendering boundaries are all different and must be managed independently.
